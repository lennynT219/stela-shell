# Imágenes — approved project assets

A primary Pi session can request **one still image from text**, or **an edit to one selected PNG**, through the official TypeScript Codex SDK. The chat model doesn't change. Generation uses Codex on this machine and OpenAI's service with the operator's existing **ChatGPT login**. There is no OpenRouter, API-key mode, paid fallback, automatic login, or gallery.

## From preview to project file

1. **Start with the idea.** «Quiero una portada para un cuento» starts a conversation, not Codex. Pi asks one or two questions about the choices that matter for *this* image: for example, «¿Qué tiene que verse en la portada? ¿Quieres transmitir calma o misterio?». For a portrait, the useful question might instead be about the subject or the light. Reply in your own words. Pi uses your answers without repeating them, proposes choices if you're unsure, and skips unnecessary questions if the request is complete or you say «elige tú».
2. **Review the prompt.** Pi combines the idea and your answers in one self-contained draft, preserving exact text and exclusions. You can request revisions or stop there. It offers a ready-to-send text block, for example:

   ```text
   Genera la imagen con este prompt:
   Portada vertical para un cuento de misterio. Una ventana iluminada en un invernadero oscuro; vista desde la senda del jardín. Acuarela en verdes fríos, con un único acento ámbar. Deja espacio para el título arriba, pero no incluyas letras.
   ```

   In the TUI, a single recognized draft is offered in the empty input editor for you to edit and send; existing typing is not replaced. Otherwise, including RPC, copy the contents of the block into your next message. **Nothing is submitted automatically.** Answering a question or saying «sí» is not permission to generate. Send the visual description, not a pointer such as «usa el anterior». If you only want a prompt, say so: the draft itself is the deliverable. If you already have a finished prompt, submit it directly with that same heading (also supported: `Generate the image with this prompt:`).
3. **Generate one preview.** Only an explicit submission containing the final visual text enables `ss_images_generate({prompt})` (**Generar imagen**). The adapter uses that current text, not a draft retrieved from previous messages. It returns the numbered preview, dimensions and original path; inline display depends on the terminal and Pi's image setting. No project copy yet.
4. Say **«guarda esta»**, **«apruebo la segunda»**, or **«guarda la vista 2 como portada.png»**. `ss_images_save({})` (**Guardar imagen**) takes *no* model-supplied path, filename, selector or approval flag. The live approval selects the exact preview and optional name. If several exist and the immediately preceding conversation doesn't identify a single preview, specify the number or «la última». «Me gusta», a hypothetical instruction or an old approval is not a save order. A direct approval needs no second confirmation.
5. The first approved save creates `media/images/` under **the working directory of this Pi session**, not a Git or Brain root. A readable default name is derived from the description. An occupied `portada.png` becomes `portada-2.png`, then `portada-3.png`; existing files are never replaced. A recorded save is reported instead of creating another copy for the same preview.

Close Pi and reopen **the same conversation** (`pi --continue` or `/resume`): the numbered previews on its active branch remain eligible. A preview descriptor (thread, basename, SHA-256, dimensions, suggested name and owner) is in the Pi tool result's `details`, not a separate index. Approvals live only in memory during the current direct user turn. Other sessions/forks, abandoned branches, changed project directories, `ss-helper`, extension-injected messages and pasted transcripts cannot carry an approval. Ephemeral `--no-session` conversations cannot be reopened. Pi may persist a resized preview in its transcript; saving **never** substitutes that copy if the original changes or disappears.

## Edit one photo

In the **Pi TUI**, submit a single message like this. Paste the absolute path Pi inserts for a clipboard image (or the path of another local PNG), without quotes or `@`, on its own line. Put the changes below it.

```text
Editar foto:
/ruta/completa/foto.png
Conserva los mismos perros, sus rasgos y su pelaje. Quita a la persona, mejora el fondo y la iluminación, y añade alas a los perros.
```

In **RPC**, send `Editar foto:` and the edit instructions in `message` and **one** `image/png` attachment in the prompt's `images` array, not a host file path. `Edit photo:` also works. No glob, directory, symlink, previous-turn selection, or model-supplied path. Only the explicit edit format takes this private input route; an ordinary chat attachment uses Pi's normal chat behavior. The input hook is not a retention policy for your terminal, clipboard, RPC client or other installed extensions.

1. The extension intercepts the direct submission before the chat prompt. It holds the selection for this turn and replaces it with a one-use text marker **without the path, instructions or attachment**. The chat model calls `ss_images_edit({})` (**Editar foto**); it cannot supply a source or approve an upload. Malformed, queued and extension-originated edit submissions do not fall through to chat. No headless approvals.
2. Pi shows the selected PNG in a local tool update (inline rendering depends on the client), its path or attachment label, dimensions and the exact changes. The confirmation explicitly asks whether to send the **whole photo**, including anyone to be removed, and those instructions to **OpenAI via Codex**. The dialog identifies the reviewed PNG by SHA-256, also in the partial result's `details`. An RPC client must display that review and return the user's decision to the matching confirmation request; use a trusted client. Declining or closing the dialog does not start Codex. Every edit, including another edit of the same photo, needs its own confirmation.
3. Only after confirmation does the adapter stage **the reviewed pixels**, not a new read of the source, as a single neutral `source.png` in that turn's private temporary workspace. It uses the SDK's `local_image` input, not a filename in the prompt. The static PNG framing/pixel limits below also apply to the input. Unneeded ancillary metadata (including text/EXIF) is stripped from the review and the staged copy. The temporary input is removed on normal completion, error or cancellation; a cleanup failure is reported. This does not delete Pi's clipboard file or data already received or retained by Codex/OpenAI. No third-party files, directories or history are attached.
4. `ss_images_edit` returns a numbered **result preview**, not a project write. Inspect it: preserving identity and every unrequested detail is an instruction, not a guarantee. The model may change details or fail to edit; no text-only substitute or automatic retry. To keep the result say, for example, **«guarda la vista 1 como perros-con-alas.png»** using the number shown. The normal save flow above also works after reopening the same conversation. The source is never overwritten.

## What goes into the visual brief

The brief keeps the requested subject, exact lettering and exclusions intact, and adds the intended format, composition and visual treatment. In the **same** Codex turn, the model translates that brief into a concrete prompt for the image tool; there's no second model call to plan the image. Explicit user choices take precedence over suggested art direction.

If the submitted prompt is for a logo representing SS in the StelaShell checkout, the adapter can explain that StelaShell is a personal AI terminal workspace on Pi, with collaborating agents and memory across sessions. It suggests two paths joining into a terminal prompt as one possible visual metaphor, legible at icon size. These are a short packaged product description and an artistic suggestion, not a read of the repository, Brain or chat history. Name **StelaShell** in full as the subject (e.g. «un logo para StelaShell») to use that reference elsewhere. The shorthand recognition is deliberately conservative: another project, a comparison or an acronym with its own definition should not inherit this identity.

For other subjects, put any meaning the image depends on in the request: **«Genera una portada para Marea, un club de lectura junto al mar; combina un libro abierto con una ola, sin texto»**. If a reference is unknown, Pi should ask what it means. Planning uses the ordinary chat, not a hidden second model; only the visual text the user chooses to submit is included in the Codex brief, not the Q&A transcript. The questions and creative choices are model-guided; requiring an explicit submission before Codex runs is enforced by the extension.

## Dependency, login and activation

- The verified host is Pi 1.6.0 on Linux with Node 24. `@openai/codex-sdk` **0.171.0** is pinned in the root manifest and lockfile. Keep npm's platform-specific optional dependencies enabled. There is no global CLI requirement or runtime install. Use the repository's normal dependency install on another machine. See the [official SDK](https://developers.openai.com/codex/sdk/) and [Codex authentication](https://learn.chatgpt.com/docs/auth).
- For first login, from the checkout with its dependencies installed, run `node node_modules/@openai/codex/bin/codex.js login` and choose **Sign in with ChatGPT** in the official flow. `node node_modules/@openai/codex/bin/codex.js login status` should say `Logged in using ChatGPT`. Never paste credentials into Pi. With no matching login, generation stops before starting a model turn. Save-only operations don't require a login, network, or quota.
- The package declares `extensions/images/index.ts`. If the profile uses per-extension development links, load `extensions/images/` through **one** route, then reload Pi. Do not add a link as well as a package registration for the same extension. If the profile has an explicit tool list, allow `ss_images_generate`, `ss_images_edit` and `ss_images_save` according to its normal permissions. The extension changes no settings or links.
- This is an operator-initiated local interaction. OpenAI's plan eligibility, quotas and product behavior can change. It is not a subscription-backed public image API or a CI service. It doesn't measure quota or promise that a cancelled or failed generation was free.

## Execution and file boundaries

- No model call at startup. The Codex home and temporary workspace must be outside the project, and the image output directory must not be a symlink. A fresh SDK thread and private working directory outside the project, one `runStreamed()` per direct generation or confirmed edit. Text generation uses an empty workspace and **never attaches files**. Editing uses only the staged PNG and the requested changes with fixed editing instructions, never Pi history, Brain or access to the source directory. No app-level retries. A user cancellation, owner change or seven-minute deadline is forwarded to the active operation; late results are discarded. Ending a turn, including a failed one, releases the cancellation listener without aborting the finished stream. A Codex error is returned to Pi without a retry. The SDK and its native runtime are trusted programs with normal account-level access to their own auth/session/image storage.
- Before generation, inspect login status and effective config with the **bundled** executable. No manual auth-file reading, credentials in messages, or modifications to user config. Do not forward API-key or provider-routing environment variables. Use the built-in OpenAI provider, a named permissions profile with only read access to the private workspace, no command approvals, shell, web search, view-image tool, apps/plugins, enabled MCP servers or child agents. Both Codex memory feature names (`memories` and its legacy `memory_tool` alias) are disabled for this invocation and checked in the effective configuration; the user's profile is unchanged. Codex merges MCP tables: disable discovered servers per invocation and recheck. Existing managed requirements still apply. Reject incompatible effective configuration (including a legacy `sandbox_mode` overriding the named profile, custom upstreams, instructions, or configured hooks) rather than weakening it. This is not a universal sandbox or a guarantee against compromised local software or simultaneous external configuration changes.
- Accept a **completed** turn with an unambiguous reported path in `CODEX_HOME/generated_images/<new-thread-id>/`. Never scan for a recent image, open arbitrary paths from prose, or copy links. Codex 0.171.0 reports the obsolete `memory_tool` spelling as an `item.completed` error item. The adapter allows its exact deprecation message once, immediately after `thread.started` and before `turn.started`. Any other warning, or the same warning repeated or emitted during a turn, is rejected. This exception does not authorize any operation or count as a successful turn or PNG. The adapter targets the observed path-as-text protocol, not arbitrary future artifact formats.
- Check static PNG framing, pixel data, dimensions and byte bounds (12 MiB, 12 million pixels, 8192 per axis; noninterlaced, 8-bit grayscale/RGB with optional alpha). Ancillary text/profile metadata is not passed to Pi in the preview; **the saved original retains all its bytes**. Re-read and verify the digest before creating any project directory. Publish from a private staging file with a hard link (atomic, no replacement); a filesystem without the necessary primitive gives an error, not an unsafe fallback. On Linux, directory file descriptors anchor file operations. Other platforms also reject redirected directories and compare identities, but this is not protection against a hostile user racing filesystem mutations. Publication and writing the Pi tool result are not a cross-file transaction.

## Checks

`node --experimental-strip-types --test extensions/images/tests/*.test.ts` exercises parsing, PNG validation, scope, collision handling, and the packaged Codex binary against a **loopback-only** service with synthetic data. A text-only Responses fixture exercises the bundled runtime’s full, unfiltered stream with the startup notice and a fictional path; it neither calls an image tool nor creates a PNG. Set `SS_TEST_PI_CLI` to the installed Pi **JS entry point** to additionally exercise real Pi RPC, a scripted question → draft → edited submission with generation only on the last turn, saved conversations and the missing-login path. The SDK shutdown regression uses a local child that emits a failed turn or waits for a real Pi cancellation; it checks that the same Pi process still accepts the next prompt. The RPC renderer fixture supplies deterministic PNG files. Photo-edit checks cover consent/decline, an attachment kept out of chat, source changes during the dialog, cleanup, save after reopening and a separate real SDK/binary transport to a local Responses fixture; the fixture does not assess a live model's editing fidelity. No test uses the operator's credentials or spends quota. The separate Linux SDK smoke test with ChatGPT validated the original path-as-text behavior; it wasn't a live test of the completed extension, the first login on a new machine, or every terminal/platform.
