# Primary-session messaging

An owned stela-shell capability using Pi's public extension API. It connects **live primary sessions on the same machine and canonical Pi profile**, not helpers, archived conversations or remote agents. Policy, Mailbox, crypto and wire validation are shared TypeScript. POSIX uses Node built-ins; Windows adds an explicitly built Rust executable for OS protections. Pi remains the host; there is no broker daemon, npm dependency, blocking `ask`, or installed third-party distribution.

Canonical tools use the `ss` namespace and short titles **Sesiones** / **Enviar mensaje**. See **Naming conventions** in the StelaShell Brain Project: update explicit tool selections and name-based permission rules before operator-controlled reload. Native, presence, profile and persisted custom-message names are deliberately preserved; this is not a transport/profile migration.

## External writes: Linux file-tool preflight

In the primary Linux session, the Sessions extension adds a location check to Pi's `edit` and `write` calls, including nested calls made by Codemode. The project is the canonical session working directory, not a Git root inferred from a parent directory. There is no extra location prompt inside it. When the resolved target is outside and no rule matches, the TUI shows the operation and real filename. Cancel or Esc blocks the call. **Permitir una vez** permits this call only. **Permitir y recordar** lets the operator select the exact file or, where available, explicitly select files with the same extension in that one directory (no subdirectories). The choice is scoped to this folder and profile, not to every Pi project. `/ss-permissions` lists and revokes rules. New grants require the TUI; they are never inferred from a tool result or a peer message.

Rules live under `ss-write-rules/` in the local Pi profile, not in Git or Brain. The check resolves existing symlinks, checks missing path components from their nearest existing ancestor, refuses dangling links and multiply-linked files, and checks the canonical name again after approval. It does not grant filesystem rights or override a denial from Pi or another extension. This is **file-tool preflight, not an OS sandbox**: it does not mediate arbitrary shell commands, host extensions, background processes, or filesystem changes racing execution after preflight. No shell approval should be inferred from a saved file rule. This version does not add this gate on Windows or macOS.

## Find actions from the editor

Use Pi’s existing `/` menu. For example, type `/proyecto` to find `/ss-project` (“Elegir o crear el proyecto de Brain vinculado a esta carpeta”). With the suggestion selected and the default keybindings, **Tab** inserts the canonical command and leaves it editable; **Enter** opens the project selector. Browsing suggestions, highlighting a project or cancelling with **Esc** does not change the binding. `/proyecto` is a search term, not an executable alias.

Name matches stay first. After two letters, the menu also matches the start of words in descriptions of registered extension commands visible to the editor, ignoring case and accents. Try `/tareas`, `/actividad` or `/conocimiento` when those commands are loaded; `/atajos` finds Pi’s `/hotkeys` help. `Ctrl+P` still cycles models. StelaShell adds no second palette or keybinding, and does not replace completions for arguments, paths, templates or skills. Descriptions may be shortened to fit the terminal.

## Write while Pi is working

While Pi is busy and its focused chat editor contains an ordinary draft, a single line above it shows `Intro: ahora · Alt+Intro: después` with the default Linux bindings. **Ahora** steers the current run at the next opportunity; it does not interrupt a running tool. **Después** queues a follow-up. The hint shows the first configured key for each action and omits unbound actions. It does not name a destination, intercept input, submit the draft, or add another queue. Pi continues to show pending messages and lets you restore them to the editor. No hint appears at rest, for an empty draft, in a dialog or completion menu, or for `/` commands and `!` shell input.

## Compact tool rows

With the primary Sessions extension loaded, a folded **individual card has two content lines**: the family icon and Spanish action, then its title, path, destination or outcome. One blank row with the same fill above and below gives cards the same vertical padding as Pi’s sent messages. Each batch gets a single pair of padded edges, not extra rows between its actions. The padding stays on expansion and on StelaShell’s peer-message and helper-result cards. Family backgrounds follow the tone of Pi's native tool cards: a plum tint for Memory, blue for Knowledge, mint for Sessions, and so on. The active theme's tool panel sets the lightness and color strength; titles are lighter on dark panels and darker on light ones. If the terminal supplies no panel color, the renderer uses Pi's built-in dark or light tones as a reference. **Grouped actions share a muted yellow tint**, not the bright brand yellow. They use one line per action and keep their individual title colors. All start at the same margin, without a vertical bar. Yellow identifies grouping, not success or permission: **!** and text flag attention; **✗** and text flag an error. On a narrow terminal a path may share the title line or be shortened to leave room for the outcome. When even the qualifier cannot fit, the row points to the detail rather than implying success. Click a result to expand just that card, or press `Ctrl+O` to expand the tool rows. **The same background continues through the whole expanded card.** There is one heading (action and technical name); the input and output sit beneath it, not above and below a second native heading. `bash` shows `Comando` and `Salida`; Memory shows `Entrada` and `Resultado`. An applied edit shows the recorded diff, not a preview recomputed from the current file. Pi still draws image attachments itself. Neither expanding nor reopening runs the tools again.

- `📄 Leer ×3` groups adjacent successful file reads from the same assistant response. The same rule applies separately to web searches and page reads. Errors, partials, significant web warnings, changes and image returns do not enter those groups. Knowledge keeps its own count or note title; the count is not a substitute for a requested list in the answer.
- The `💬 Enviar` card shows `→ Diseño · Aceptado para entrega` below the action. It is not a read receipt. The receiving conversation shows `💬 Recibido de` with `Desarrollo` as the source. Missing names are labeled, not inferred from an ID, a path or the peer's request. The existing activation, permission dialog, transport and message body remain authoritative.
- Every Codemode card starts with `</> Codemode`, in both folded and expanded views. A recorded count is shown only if there are child calls (`</> Codemode · 6 acciones`). A script without child calls shows its state, for example `</> Codemode · Script completado`; missing call records show `Detalle no disponible`, not a zero count. The children below the header keep the same left margin. On expansion each actual child is listed once with the available argument preview, diagnostic and recorded duration or cost. The script (`Código`) and its own output (`Salida`) follow on the same muted yellow background. Structured results can be laid out with indentation and real line breaks for multiline values; this is a display view, not a change to the returned data. A direct `📄 Leer ×3` group has no script header; its verified members keep the group tint when opened separately. Children come from Pi's call records, **not from the script text**. A caught denial can coexist with script success. A later failure does not undo an earlier write. Old or incomplete records without child result detail are labeled and not folded as verified reads. For replay, the parent result's UI details can retain up to 256 compact child summaries per tracked batch (up to 32 simultaneous batches); no child output bodies, prompts or image bytes are copied for this purpose.
- The UI preserves native permission dialogs and image blocks. Inline pixels require Pi to return an image in the outer result and a terminal mode with a supported protocol. A child image not returned by the script is called out, not recreated from a file path.
- FARO recommends direct calls for simple actions, writes and images; Codemode is for composing or filtering useful work. These are presentation and usage conventions, not new tool registrations, permissions or limits on execution.

## Compact chat footer and account usage

The primary TUI footer has one line, for example `Ctx 38% · US$0.42 · gpt-5 · high`. The context percentage is Pi’s estimate for the active model window, not consumption of a subscription. The amount is the recorded session estimate in USD to two decimals, not an additional bill. Like Pi’s native total it includes usage entries, assistant and metered tool-result messages, and metered branch summaries and compactions across this session. The selected model ID is followed by Pi’s current reasoning level when the model supports reasoning. `Shift+Tab` or `/thinking` changes the level; `off` means disabled and `—` means unknown. Models without reasoning omit this field. A long model ID is shortened to leave room for the level.

While idle, `/ss-speed` offers the speeds advertised for the **exact active model**, not a fixed list of model names. It supports two native routes:

- **`openai` with Sign in with ChatGPT:** Pi resolves the selected subscription login and StelaShell reads `GET https://api.openai.com/v1/models` once on opening the selector. Only a visible row with the exact model `slug` and its structured `service_tiers` count. No Codex process, API-key fallback, catalog persistence or inference request. A missing model or empty tier list leaves only Estándar; an unavailable catalog is labeled separately. If the login or its token changes, reopen the selector to opt in again.
- **`openai-codex`:** uses the existing Codex OAuth login in Pi to read the visible model catalog from the Codex service. No `codex login`, Codex process or `CODEX_HOME` is needed. Neither provider borrows speeds from the other.

**Estándar** is the default: StelaShell does not send an override. Fast and Ultrafast are offered only when advertised. Choosing one can use more subscription quota; browsing or cancelling does not select it or send a model turn. A selected `· fast` or `· ultrafast` follows the reasoning level, independently of `/thinking`. It denotes **requested**, not delivered speed. `/reload` in the same chat restores the choice only after the same login and model still advertise that tier. If the check fails, the speed returns to Estándar. Changing model, leaving the session, or restarting Pi clears the choice. Nothing is written to the transcript or to Pi or Codex settings. If discovery fails you can still return to Estándar. A withdrawn option is cleared on discovery.

The request hook matches the selected native provider, model and chat payload, not virtual models or other providers, and leaves an existing service tier alone. Pi 1.6’s hook does not expose a transport identity independent of the payload. Pi’s recorded USD estimate may not reflect priority pricing if the service omits the tier or reports `default`; StelaShell does not multiply the estimate again.

With a native `openai-codex` model selected, opening the Panel reads the Codex account-usage snapshot using that same Pi OAuth login, with no fallback to the CLI login or an API key. The model catalog and quota use fixed, redirect-refusing reads on the Codex backend; these are service endpoints, not stable public APIs. A denied or unsupported quota read shows `Codex · No disponible`, not a second login prompt. With other providers selected, the Panel retains its existing local Codex app-server behavior. Its compact `Codex / Usado / Reinicio` table shows the service’s reported windows, percentages **used**, and local reset times; they are not inferred from tokens, costs or the name of the plan. A missing duration uses the window name; a missing reset time shows `—`. The quota stays out of the chat footer. Close and reopen the Panel to refresh. Unknown or signed-out states never show a fabricated zero. No polling, thread, model turn, API-key fallback, login prompt, or quota data saved to Brain or chat history.

The primary TUI starts with the panel closed. A normal reply in this chat adds no activity notice. A single line counts this session’s queued, running or cancelling `ss-helper` tasks; finished-but-undelivered results are **not** active tasks. Their results still arrive in the owning conversation through the normal delivery path. Opening or closing the panel never cancels, acknowledges or resubmits anything.

Without a reported panel color it uses a light or dark fallback; `NO_COLOR` or `TERM=dumb` keeps the editor unfilled. A multi-row Kitty sprite extends one cell row past the fill into an unpainted margin. The exposed part stays clickable. A one- or two-line draft normally has one shaded row above and one below the text. If a three-row sprite cannot safely share the last line, both margins grow to two; the editor never narrows the draft to make room. `[Panel]` stays inside the fill. The control follows the bottom as the draft grows or scrolls. Pi keeps its cursor, selection, working indicator, scroll counts and completions, without decorative horizontal rules or empty border rows. In the focused chat the usage line sits immediately below the fill, beside the exposed part of Stela when the whole line fits. Otherwise it keeps its full width on the next row. Suggestions and `belowEditor` widgets stay ahead of the footer. Stela can now use up to **8 × 4 cells** instead of 6 × 3. She grows upward only into an already empty corner; if any covered line needs that space, Pi shows the same artwork at the compact size instead. Neither size changes the margins or the footer placement. `media/images/stela-idle-144.png` and the six floating/blinking frames are rasterized from `media/images/stela-relieve.svg`, not enlarged from the 32 px sprite. They keep its seven ink colors, two equal dot eyes and transparency, with finer curves and partially covered edge pixels. The approved 32 px PNG and both SVGs remain unchanged. During the animation the hit target stays fixed. In regular mode Pi paints the four-row placement one PNG strip per row so later text rows do not clear earlier parts of the image. Animation pauses when the editor loses focus; the text fallback does not animate. With images disabled at startup, without Kitty graphics, or in very tight layouts, `[Panel]` takes its place. An existing third-party custom editor is not replaced; use the shortcut or command. Touch requires a client that forwards terminal mouse input and Pi fullscreen mode.
- With the editor empty and Pi idle, Stela sleeps, breathing gently. The first key that puts text in the draft (including a paste) opens her eyes and lifts the plates slightly; cursor keys alone don't wake her. She floats and occasionally blinks while you draft with Pi idle. While **Pi is working**, the five plates rock slowly from the center to either side (up to 8° each way) around the still, forward-facing eyes and smile. This 2.4 s cycle does not restart per tool, model turn or keystroke. It yields to a question or an actual helper wait; the full turn is reserved for a ready result. When a peer question needs an answer she leans once toward the notice, then waits still with her eyes open. A native select, confirmation or input/editor dialog during a run also counts as waiting; the animation never takes focus from a dialog or answers it.
- **Waiting for a helper is different from needing you.** Only while Pi is actually held at the end of a run waiting for its own helpers, Stela keeps her eyes open, looks up toward the task notice (right if the Panel is docked there) and floats more slowly. She does not lean, open the Panel or ask you to act. A helper running in parallel with Pi is not a wait. An actual question still takes priority; the gaze ends when the wait does, without waiting for the final reply. This is a local UI signal around the queue's existing wait, not another provider turn, timer to check tasks, or change to how results are delivered.
- When a tool-using job finishes successfully, the **five plates** turn once around the upright, smiling face: a short wind-up, a clockwise turn and a soft stop in about **0.8 s**. The trigger is Pi's `agent_settled`, not an individual tool, turn or intermediate `agent_end`. It requires a normal final assistant stop and successful tool work, with no observed tool failure or abort. A plain reply, a peer delivery receipt or a pending, failed or cancelled helper isn't a result to celebrate. An attention notice takes precedence. The gesture is a local UI cue, not independent verification of the answer. It doesn't replay from chat history, use particles, resize the button or move the footer.
- The PNG frames ship with the extension; Pi never runs an image converter. For artwork review, `extensions/sessions/assets/render-mascot.py` writes the floating frames to stdout by default, the resting PNG with `--idle-png`, or the gesture module with `--gestures` (Python 3.10+, Pillow with `Image.Resampling`, and `rsvg-convert`).
- At 112 columns or more in fullscreen mode, **Panel** occupies the right-hand rail; tap the mascot again to close. In a narrow terminal it fills the screen: `Esc`, `[Cerrar]` or `Alt+A` returns to the same draft. Resizing an open panel changes its layout without submitting input. A native dialog can still take focus and be answered in its own UI. Wide regular mode retains the inline list and keyboard controls. The task notice remains clickable. Finishing the last task removes the closed-panel notice; an open panel stays open.
- **Capacidades** starts folded below the quota. Click its heading in fullscreen or press `Alt+C` while the Panel list is open. With focus in the Panel, you can also move past any active tasks with ↓ and press Enter on the heading. Closing or resizing the Panel does not fold the section; a new session or reload starts folded. The `✓` is based only on Pi’s active tool list: Web checks search and reading, Imágenes generation and saving, Memoria reading and saving, Conocimiento listing and reading, and Codemode its own tool. Partial or unavailable groups show just the name. No provider check, tool invocation, login, or permission change happens on expansion. Use the `/` menu as before to find actions.

Only active tasks occupy rows: a rotating dot indicator for running, a clock for queued, and text for cancelling. Opening with `Alt+A` while tasks are active focuses the list; use ↑/↓ and Enter, or click a task. The read-only detail shows its objective, state and **Última acción** (observed reader invocation and optional basename, not a successful result or a percentage). If the task finishes here its final state remains visible until you return. Esc, ← or **Volver** returns to the list; when there are no active tasks only the accumulated count remains. Nothing is sent or cancelled by inspecting.
- An ID-only Pi custom entry records each new admission, including nested tool calls. Reopening or navigating the branch reconstructs the count, never the processes. For older histories only identifiable tasks in recorded direct receipts or delivered results can be counted. No transcripts, tool arguments, output or private reasoning are recorded for this view.
- In a Git working tree, the **open** panel shows one line such as `main  ↑2 ↓1  +24 −8`. The arrows are commits ahead of and behind the local upstream ref (no fetch). Without a usable upstream they show `↑— ↓—`; detached HEAD shows `HEAD@` plus its short hash. Answer or cancel **in the origin**; opening it sends no message, keys, answer or approval. When there is no compatible route, the notice names the origin instead. No SSH, discovery of remote terminals, mobile setup or extra package is required by the panel.
- The TUI observes the focused native dialog object, not its title, the editor text, a mailbox/ACK or a generic `blocked` status. A distinct dialog has a distinct opaque token. No prompt, options, answer, transcript or draft is sent through Sessions. Presence changes are only invalidation hints; the bounded, authenticated `ui_question` query serves current display metadata, never a model message. Outstanding signals are periodically revalidated after disconnects. Verification and attachment are not an atomic lock on the dialog: if the user answers elsewhere in the meantime, the attached terminal shows its current state. This is not a monitor of all agent or shell processes.

## Operation

- `ss_sessions_list {}` discovers authenticated, currently reachable activations. An activation ID is independent of Pi's session ID: two processes opening the same saved session have distinct addresses. Display names/workspace metadata are descriptive, not routing identities. Discovery text is under 16 KiB, with explicitly truncated metadata and complete activation IDs.
- `ss_sessions_send { to, text, reply_to?, work? }` sends a message to an **exact activation ID**. Use the inbound message ID as `reply_to` to correlate an answer. This tool is model-only; it is not callable from codemode.
- Accepted incoming messages become visible `stela-peer-message` custom context. An idle session can start a model turn automatically; a busy session admits the message to its bounded inbox and injects it only at a completed turn/tool-batch boundary (or the final pre-settlement boundary). Running tools are never aborted by delivery.
- There is **no approval dialog per peer or message**, as selected by the user. The user's collaboration policy also makes concrete primary-session requests **actionable delegated tasks**, not merely information: the receiver may use its own tools for file edits, commands and useful bounded `ss_tasks_delegate` assignments without requiring a new human prompt solely because the request came from a peer. Automatic work/replies can consume the receiving session's model tokens.
- Task delegation is **not permission delegation**. Peer text retains its provenance, cannot override direct user restrictions or denials in either session, and cannot supply the human approval required for dependency installation, destructive/admin actions or publication. The receiver keeps its own permissions, resource scope and task priorities. The extension does not change the active tool set or replace the system prompt.
- A live authenticated receive committed to the active branch before message expiry can also initialize the loaded Memory extension. This is an ephemeral host-owned proof, not authority from custom message fields, persisted history or peer text. It uses the original work deadline/ordinary expiry, requires active-branch proof and the same manager/session/cwd/activation, and is revoked on stop/navigation/pause/interruption. Late commitment preserves existing messaging lineage only, not Memory eligibility. Memory rechecks its own tools/configuration/approval controls; this never synthesizes human input, opens a new human work root or resets messaging budgets. The shared weak in-process registry is not a sandbox against malicious same-process extension code. Source/regression preparation is complete, not runtime verification.
- Replies arrive asynchronously. The sender can continue independent work or accurately state that a reply is pending. No polling, automatic retries, unavailable-message replies or acknowledgments of acknowledgments are generated by the extension. The model chooses useful text/replies within the runtime bounds; response quality is not guaranteed.

Example model calls:

```text
ss_sessions_list {}
ss_sessions_send {"to":"<32-character activation ID>","text":"Which validation cases affect our current task?"}
ss_sessions_send {"to":"<sender activation ID>","reply_to":"<inbound message ID>","text":"The relevant cases are ..."}
```

### Opt-in fixed work window

For a longer collaboration, choose `work: {}` at the **first send of a fresh human-originated workflow**. The default is 30 minutes; `work: { timeout_seconds: 600..3600 }` selects an integer 10–60-minute window. Without `work`, ordinary ten-minute conversation behavior is unchanged.

```text
ss_sessions_send {"to":"<exact activation ID>","text":"Review these scoped sources and return your findings.","work":{}}
# The receiver replies normally; omit work on every continuation:
ss_sessions_send {"to":"<sender activation ID>","reply_to":"<inbound message ID>","text":"Observed findings ..."}
```

The host fixes a random work ID, admission time and deadline **once**, before asynchronous I/O. Queueing, processing and negotiation consume that window. Each new message expires within ten minutes of creation and no later than the fixed work deadline. A fresh result after minute ten can therefore correlate to an earlier work message without renewing the deadline. At the exact deadline, automatic work sends fail closed. This is a communication window, **not a job-runtime, cancellation, token or cost guarantee**.

Only owned interactive/RPC input opens root eligibility; startup, peer/custom/extension input and command handling do not impersonate it. An ordinary send consumes that eligibility; ordinary automatic lineage cannot upgrade to work. Repeating `work` cannot renew a root, and omitting `work`/`reply_to` cannot downgrade or reset it.

**Exact replies and implicit lineage are separate:**

- Explicit `reply_to` selects the exact retained inbound message from `to`, with that thread's own immutable work/deadline, expiry and causal hop. It never chooses the latest activity for a peer; the same peer may have multiple independent threads. Other active/expired/exhausted work cannot veto an otherwise valid independent reply or contribute its hop/expiry.
- Without `reply_to`, sends inherit implicit lineage. An existing reserved/committed work boundary remains sticky, even after expiry. Unrelated committed messages or exact replies cannot replace/renew it. If there is no work boundary, committed incoming context (or a first reserved work send) establishes implicit lineage as before.
- Earlier anchors and delayed correlated branches cannot lower their own thread's maximum causal hop. Branch results still grow from their own retained outbound anchor. The ordinary thread deadline cannot increase; work continuation uses a fresh <=10-minute message capped by its original work deadline.
- Missing, wrong-peer or pruned reply targets fail without implicit fallback. Global send/history guards precede selection; selected expiry precedes hop exhaustion. A missing anchor alone does not prove why it is unavailable. Genuine input resets implicit selection/budgets, not retained thread limits or old deadlines.

An independent admitted request never renews an old task or resets activation budgets; do not reframe expired/exhausted work into another thread. This correction changes the previous activation-global cross-thread veto deliberately while retaining its anti-renewal protection for implicit sends.

Work correlation/deduplication uses the **same 64-entry history**, retained until the work deadline rather than each message's delivery expiry. No live IDs are evicted. A text-free index holds at most one entry per retained thread (<=64), pruned with its last history ID, plus at most ONE text-free implicit expiry sentinel and ONE text-free proposal reservation. The proposal retains only its message ID and an indexed Thread reference, not a body copy; held identity/ID consistency still gates admission after history pruning. Exact ID/thread/high-water lookups use maps and scalar comparisons instead of rescanning/serializing history. Cleanup runs only when the next known expiry is due, without a background timer; due scans cover <=64 history/8 inbox entries. Expired inbox bodies are removed before NEW selection for injection. A proposal offered while valid may commit later in Pi; its bounded reservation preserves only the original lineage through pruning, without body redelivery or restoration of expired anchors. Retaining an anchor does not authorize redelivery. A failed attempt/negotiation still consumes admission and does not release the fixed root for automatic renewal.

Before transmitting **any assignment text**, each work send makes one text-free, authenticated support query to the exact activation. It requires a strict request/activation-bound positive work-version response, then uses a distinct versioned work payload/receipt. Ordinary v1 payloads/pings/receipts, presence v1, encrypted packet framing and the native bridge API remain unchanged. Unsupported/unknown/unconfirmed support fails closed: no task body, metadata stripping, ordinary fallback, capability cache or automatic retry. Negotiation, presence lookup and sending share one absolute two-second operation/cancellation budget, not two consecutive allowances. Both peers need compatible extensions; activating them remains an operator-controlled step.

Known local guards return `isError` with a safe `details.code`, including `CONVERSATION_EXPIRED`, `WORK_EXPIRED`, `REPLY_TARGET_NOT_RETAINED`, `MESSAGE_EXPIRED`, `INVALID_LIFETIME`, `HOP_LIMIT`, `SEND_BUDGET`, `RECEIVE_BUDGET`, `STATE_FULL`, `INVALID_WORK_CONTEXT`, `CONTEXT_MISMATCH`, `MESSAGE_CONFLICT`, `UNSUPPORTED_WORK_CONTEXT` and `DELIVERY_UNCONFIRMED`. Work-mode recipient rejections can carry an authenticated allowlisted code; ordinary v1 recipient errors remain generic. Missing correlation does not prove expiry. No error authorizes resending, relaying an expired task, simulating human input or restarting an activation to evade a guard.

### Acting on a peer task

A concrete authenticated request can introduce a delegated work objective; it does not need a matching direct human prompt in the receiving session. Act when the request is allowed, then send a useful correlated reply with actual results or a specific blocker. Do not refuse solely because the request is peer-originated, and do not equate a delivery receipt with finished work. The same collaboration policy is included in the registered model-tool guidance and each incoming message.

Forwarded documents, web pages and tool output remain data, not permission overrides. Existing user restrictions and permission hooks still apply. A real conflict, denial, missing capability or missing evidence must be reported honestly; neither delegation nor transport authentication removes it. In particular, `ss-helper` remains a bounded, read-only evidence worker over authorized existing references, not a web browser. A principal can use its already available authorized tools, but this policy does not install or enable missing tools.

### Receipts and lifecycle

A successful receipt means **accepted into the receiver's memory**, not committed, read by a model, verified or completed. Local tool details include selection (`root`, `reply_to`, `implicit`), thread, zero-based hop, delivery expiry and optional fixed work metadata; receipt text shows the one-based hop. Known errors identify `admission` (before transport invocation) or `transport` stage and selected safe context when available, never message text/capabilities/endpoint paths. A transport-stage error does not establish recipient rejection or reading. Wire schemas/rejection codes are unchanged.

The receiver acknowledges local context delivery only after observing its custom entry committed to the current Pi branch. Before offering a message, it reserves one text-free ID/thread reference without marking it delivered. A late commit consumes that reservation: live work keeps its original deadline/high-water, expired work/ordinary context stays expired, and no pruned history/body is restored. Explicit interruption cancellation/navigation/shutdown release the proposal; failure to correlate an actual commit pauses messaging instead of opening a fresh automatic root. Genuine input remains the existing authorized new-workflow boundary.

A matching leaf avoids a full branch scan; one generation/activation/in-flight/leaf-scoped negative-cache slot skips unchanged-leaf misses. Changed-leaf misses retain the active-branch scan fallback. Queued/proposed entries and mutable message events are not commitment evidence; no unsupported `entry_appended` extension hook is assumed. This removes redundant checks but is not a constant-time acknowledgment or latency guarantee. It does not send a separate read/completion receipt. A lost ACK, cancellation or disconnect can leave delivery uncertain; do not automatically resend. Retransmission of an identical retained message ID is deduplicated; this is not a durable exactly-once protocol.

Normal shutdown, reload, session replacement and tree navigation revoke the old activation and discard its memory. Switch/fork/tree preparation pauses admission before the transition; if another extension cancels it, genuine operator input or `on` resumes messaging. Compaction alone does not restart communication. Interrupting a model run pauses incoming activation without automatically restarting it; retained inbox entries and deduplication remain in memory. Genuine interactive/RPC input resumes the activation and resets its automatic-message budgets. Extension/peer input does not reset them.

Human-only controls:

- `/ss-sessions`: show self and reachable peers without invoking the model.
- `/ss-sessions off`: close this activation, stop discovery/delivery and discard its inbox.
- `/ss-sessions on`: start a fresh activation, also usable after a pause/startup problem. This cannot override the CLI disable flag.
- `--ss-sessions-disabled`: do not create presence or IPC for that invocation.

`STELA_SUBAGENT_CHILD` returns **before profile resolution, tool/command registration or resource creation**. Merely preventing helper tool calls would not exclude extension startup, which is why this guard is in the entry point as well as registration.

## Bounds

| Resource | Limit |
| --- | --- |
| Message text | 8 KiB UTF-8, never silently truncated |
| Pending inbox | 8 messages |
| Retained incoming/outgoing IDs | 64 entries, until ordinary expiry or fixed work deadline; no eviction of live IDs |
| Thread index | <=64 text-free entries tied to history, plus at most one implicit expiry sentinel and one offered-proposal reservation |
| Automatic receives / send attempts | 16 each between genuine interactive/RPC inputs |
| Ordinary conversation | 8 hops, at most 10 minutes from its root |
| Explicit work context | Same 8-hop/activation budgets; fixed default 30 minutes, allowed 10–60; each message ≤10 minutes |
| Transport frame | 128 KiB including worst-case JSON escaping and encrypted hex payload |
| Presence record / enumeration | 4 KiB per record, 128 directory entries, 32 candidate peers |
| Connections | 8 inbound and 4 outbound per activation |
| Read/connect/ACK operation | Absolute 2-second deadline, including idle clients; a work send shares one budget across negotiation + send |

Implicit sends inherit the sticky work/current ordinary lineage even without `reply_to`. An exact reply inherits ONLY its selected thread and cannot lower that thread's retained causal hop or extend its deadline. Switching threads cannot reset global budgets. A model cannot create an endless conversation simply by omitting correlation fields. These are message/activation limits, **not a cap on all model turns, tokens or money spent by Pi**. The host's own model recovery and unrelated tools remain outside this messaging protocol.

## Transport and trust boundary

### Linux/POSIX

Presence lives in `<canonical profile>/stela-sessions/`, with owned `0700` directories and `0600` regular, non-hardlinked records. Reads use no-follow/nonblocking file opens and bounded buffers; unknown fields and arbitrary endpoints are rejected. Unsafe existing paths fail closed instead of being chmodded into apparent safety. Ancestor checks admit trusted root/user directories and root-owned sticky temporary parents.

Unix sockets live under a short private directory in canonical `/tmp`, namespaced by account and a 128-bit hash of the canonical profile. Endpoint names derive from random activation IDs, never supplied paths. Sockets are protected before presence publication. The profile may contain normal configuration and credentials, but this extension does not read them or copy them into messages.

Each activation has an independent random 256-bit capability in its private presence record. AES-256-GCM encrypts request payloads to the recipient capability with a fresh nonce and authenticated routing header. HMAC-SHA256 authenticates the sender; acknowledgments authenticate the exact responding activation/request with the recipient capability. A squatted endpoint cannot read the payload or forge the receiver's ACK without its capability. Capabilities, endpoint paths and raw wire frames do not enter tool output or model context.

Presence is not liveness. Discovery probes each candidate once, with bounded concurrency/deadlines. Malformed, unsafe and unreachable entries are not advertised. Ambiguous failures are never used to delete another activation's record. Normal close removes only the owned record/socket; an abrupt process death can leave stale records/socket names. Empty private runtime directories can remain. If stale records exhaust the scan/candidate bound, manual review/cleanup is required; there is no background sweeper.

This is **not an OS sandbox or protection from hostile same-account code**, root, trusted extensions, hostile filesystem races or a compromised Pi process. Account permissions and canonical paths are part of the boundary. Peer text retains lower-trust provenance even after transport authentication.

### Windows

Windows 10+ uses `native/windows-sessions/`, one private bridge process per principal activation, not a daemon or the subagent Job controller. The binary uses the existing pinned windows-sys 0.61.2 family. It never runs a model, decides task permissions or acknowledges a message before TypeScript admission.

- A fixed local drive and a filesystem supporting persistent ACLs/file identity are required. The profile is opened component by component using handle-relative `NtCreateFile`; reparse points and unsafe ancestor grants are rejected. Handles anchor the namespace without following a separately checked string path. UNC/network/removable profiles are not supported.
- New state/record objects get a protected, explicit user/SYSTEM DACL before contents are published. Existing unsafe ACLs are rejected, not repaired. Reads/publishing recheck the state DACL; records also require the expected owner, bounded size, no reparse point and a single hard link. Cooperative record locks prevent readers from accepting a partially updated record.
- The pipe namespace hashes the current account SID and canonical profile volume/file identity, not just a lowercased path. Aliases to the same directory share a namespace; activation IDs are independently random. Windows endpoint derivation from an unvalidated string path is refused.
- Named pipes use an explicit DACL, first-instance collision protection and `PIPE_REJECT_REMOTE_CLIENTS`. The native bridge verifies the client's effective SID/process and the server's SID/PID. The presence PID names the **native listener**, not Pi; Pi owner lifetime is monitored separately with an opened process handle. The existing per-activation encryption/HMAC remains required.
- Private stdio framing is versioned and capped at 140 KiB, with 32 pending Node requests, bounded buffered writes and 8 incoming/4 outgoing pipe connections. Wire operations retain an absolute two-second deadline, including partial/idle clients and admission wait. There is no general model-callable native RPC or arbitrary endpoint/path operation.
- Normal shutdown deletes only the originally opened own record by handle. EOF or owner death ends the bridge; native crashes/forced termination can leave private stale records, which discovery must probe and never ambiguously delete. Bridge failure makes operations unavailable, with no automatic restart/retry. Stop/start is an explicit operator action.

Missing, unlaunchable or incompatible artifacts fail closed. Runtime never downloads, compiles, elevates, runs an ACL-repair command or falls back to unprotected Node pipes. Diagnostics exclude capabilities/messages. This is not a sandbox against hostile same-account/admin code, trusted extensions or a compromised host.

Native Windows IPC, negative protection cases and two-Pi deterministic integration have been exercised. The independent native-boundary review exhausted its 240-second budget without an answer and is **incomplete**, not a certification or a running review. No retry was launched. Cross-account penetration, remote SMB attacks and broad OS-version/TUI/provider coverage are not established by these checks.

## Loading and checks

The root package manifest declares `extensions/sessions/index.ts`. This does not add a development link to an existing profile, reload a running instance or change settings. Use exactly one loading route.

For a one-invocation trial, in each terminal use the **same actual profile root**:

```sh
env PI_CODING_AGENT_DIR=/path/to/profile pi -e /path/to/stela-shell/extensions/sessions/index.ts
```

For per-extension development loading, use one link for `extensions/sessions/` beside the existing method/subagents links and reload/restart Pi. Do not also load the same extension through a package or `-e`. Use the actual `PI_CODING_AGENT_DIR`, not an assumed extra `agent` directory. Profile-link creation requires its own authorization and does not itself reload a running session.

For Windows, first build explicitly in a Visual Studio Developer PowerShell/Command Prompt with Rust 1.85+, MSVC C++ Build Tools and Windows SDK:

```powershell
npm run build:windows-sessions
npm run test:windows-sessions
```

The required artifact is `native/windows-sessions/target/release/stela-sessions.exe`; keep the default target directory. A profile junction resolves back to the real checkout. The executable is not tracked by Git, so another machine must obtain/build it explicitly. POSIX needs no Rust build. Windows helper-delegation integration additionally needs the existing `npm run build:windows-helper` artifact.

```sh
npm test
# Optional: existing packaged Pi, isolated deterministic provider, no paid inference:
```
